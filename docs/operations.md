# 運用と復旧

## GSC取得の比較モード

取得処理の引き継ぎ確認は [collection.md](collection.md) を参照。`gsc_compare=true` は手動限定・外部書込なしで、`publish=true` と同時には使えません。既定と定期実行では、従来のSheet読取・ページ更新を継続します。本番の取得切り替えは別工程です。

## 日常の確認

- 画面の「データ最終日」と「ページ更新」を区別する。GSC確定値の遅延により、集計は直近の日曜まで含まれない場合がある
- ページ更新は実行が正常に終わった時点。元データが増えていない場合はデータ最終日が変わらない
- データ最終日から14日を超えると、ページ閲覧時に注意を表示。公開が止まっても、古いページ側で判定する
- Actionsの実行結果で `build` → `deploy` → `verify` を確認。`verify`未成功を「公開確認済み」と扱わない

## エラー時

| 内容 | 対応 |
|---|---|
| Google認証／403 | 専用アカウントへの対象シート共有、WIF条件、API有効化を確認。鍵の追加や権限拡張で迂回しない |
| `STALE_DATA` | 既存GASの実行日時と結果を確認。古いデータを新しい取得結果として公開しない |
| `DUPLICATE` / `MISSING_DAY` | 元シートを確認。自動で削除・ゼロ補完せず、原因を直してから手動確認 |
| `TOTAL_MISMATCH` | 日次と検索語の期間・取得条件を確認。GSC側の仕様による差も考えられるため、数値を無理に合わせない |
| `HISTORY_LOSS` | 古い履歴や最新週が欠落していないか確認。16カ月の取得範囲だけでシート全体を置き換えない |
| `git push`失敗 | 他の変更やブランチ制限を確認。force push・自動rebase・保護解除は行わない |
| 公開後の検証失敗 | 公開自体は済んでいる可能性がある。配信内容とPages実行状態を先に確認し、無断で再公開・旧版復元しない |

定期更新だけ止める場合は `SCHEDULE_ENABLED=false`。全実行を止める場合は `AUTOMATION_ENABLED=false`。実際の停止・再開は運用担当者の判断で行います。

手動実行は既定の`publish=false`で確認でき、その後の公開は`publish=true`。生成コードは元Sheetへ一切書き込みません。

## 長期停止・担当交代

公開リポジトリでは60日間活動がないと定期実行が無効になることがあります。正常更新で生成HTMLをコミットしますが、障害による長期停止は自動解消しません。Actions画面でワークフローを有効化し、原因解決後に手動確認してから再開します。[GitHub公式仕様](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)

担当交代時は、会社リポジトリの管理権限、Google Cloud・元シート・GSC・GASの管理者、ワークフローの通知先を確認します。定期実行の通知はcronを最後に編集したユーザーと関連するため、通知を会社全体に届くものと仮定しません。Slack通知はこの構成に含みません。

## 集計や施策イベントを変更する場合

`template.html`のイベントまたは`src/dashboard.py`の分類を修正し、合成テストと同期間の実データ照合を行います。ページ確認後に反映します。実行ActionのSHA更新もコード変更として確認します。

元データ・認証ファイルはリポジトリに入れません。Actionsは一時領域に取得して削除し、公開用HTMLのみを1日保持のPages artifactにします。秘密値や検索語全件を診断ログへ出さないでください。
